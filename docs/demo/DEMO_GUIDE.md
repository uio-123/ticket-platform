# 五分钟演示指南

## 演示前检查

1. 已执行 `docs/sql/01-ticket-schema.sql` 和 `docs/sql/02-demo-data.sql`。
2. Redis、RabbitMQ、Nacos、MySQL 已启动；`event-service`、`order-service`、`payment-service` 已注册。
3. 用 `docs/http/ticket-demo.http` 的第 4 步预热 Redis。未预热时抢票返回“场次尚未预热或未开售”，这是预期保护行为。

## 推荐讲述顺序

1. 打开 `/shows`、`/shows/1001/sessions` 和票档查询，说明商品模型已拆为演出、场次、票档。
2. 执行预热和抢票请求，说明 Lua 在 Redis 内一次性完成余票和限购判断。
3. 轮询抢票结果，展示请求先返回排队状态、再由 MQ 消费者异步建单。
4. 走普通订单路径并调用模拟支付，展示待支付订单变为已支付、订单服务生成电子票。
5. 调用验票接口两次，展示第一张成功、第二次被拒绝。
6. 说明未支付订单由订单服务每分钟扫描，超过 15 分钟条件更新为已取消并回补票源。

## 四个必演异常

| 场景 | 操作 | 预期 |
| --- | --- | --- |
| 售罄 | 将预热库存设为 0 后抢票 | 返回“票已售罄” |
| 限购 | 同一用户、同一场次请求总数超过票档限购 | 返回“超过场次限购数量” |
| 重复验票 | 对同一 token 调用两次验票 | 第二次返回“电子票不存在或已核验” |
| 超时回补 | 创建订单后不支付，等待超过 15 分钟 | 订单取消，票档可售库存恢复 |

## 排查路径

- `QUEUED` 不变：检查 RabbitMQ 的 `ticket.rush.request.queue` 是否有消费者及订单服务日志。
- 支付后无票：检查 `ticket.pay.direct`、`ticket.pay.success.queue` 和订单服务消费者日志。
- 订单创建失败后 Redis 余票不一致：检查 `TicketRushListener` 的异常与回补日志；消费者失败会将预扣余票和用户计数回补。
- 服务无法启动：优先检查 Nacos 共享配置是否提供 `ticket.db.host`、`ticket.db.pw`。

## 演示边界

支付接口为内部模拟，电子票 token 用于演示一次性验票；它们不代表真实支付渠道、动态二维码或生产级验票系统。
