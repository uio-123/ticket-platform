# 简历表述与面试问答

## 简历项目描述

> 基于 Spring Cloud Alibaba 构建赛事与演出票务平台，完成演出/场次/票档建模及票务订单闭环；针对热点场次采用 Redis Lua 原子预扣与场次限购，结合 RabbitMQ 异步建单、消费幂等和失败回补防止超卖；实现 15 分钟超时关闭、模拟支付成功事件、电子票生成和一次性验票。

## 可量化表述边界

- 可以说：实现了 Redis Lua 预扣、MQ 异步建单、订单条件更新和库存补偿机制。
- 不应说：已经接入真实支付、支撑生产级百万并发、完成了选座或复杂风控。
- 压测数据必须在实际执行后填写；未压测时不虚构 QPS 或库存规模。

## 高频问题

### 为什么秒杀主链路不使用 Seata？

Seata 更适合普通下单的分布式事务。热点场次的高并发入口先用 Redis Lua 将库存校验、限购和预扣压缩成单次原子操作，再用 MQ 异步落库；数据库失败后补偿 Redis，选择最终一致性以降低 MySQL 压力。

### 如何防止超卖？

入口层 Lua 防止 Redis 余票变负；消费者落库时调用票档条件扣减，要求 `available_stock >= quantity`；消费者创建订单失败则回补 Redis 库存和用户计数，形成入口、落库、补偿三层保护。

### 如何保证 MQ 消费幂等？

每次抢票生成 `requestId`，消费者使用 `ticket:rush:consumed:{requestId}` 的 `SETNX` 作为消费幂等键。支付状态和验票也通过数据库条件更新，重复事件不会重复改变状态。

### 支付成功事件重复发送怎么办？

订单只允许 `PENDING_PAYMENT → PAID` 一次。出票前先查询已有电子票；已出票时直接返回已有记录，因此重复支付消息不会多出票。

### 未支付订单如何释放库存？

订单服务定时扫描创建时间超过 15 分钟的待支付订单，以条件更新改为已取消；只有更新成功的订单才回补票档库存，避免并发支付和取消双重回补。

### 当前项目有什么边界？

当前只实现按票档售卖与内部模拟支付。选座、退款、实名第三方核验、主办方后台和生产级风控都是明确的后续扩展，不把未实现能力包装为已完成能力。
